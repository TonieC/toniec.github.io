Introduction

Tflows

A registry-driven scripting framework for discord.py bots — write commands as short text scripts, resolve them against a shared FunctionRegistry, and extend the whole system with your own Python functions and variables.

Quick Start pip install tflows

What is Tflows?

Tflows is a lightweight Python framework built on top of discord.py 2.x that lets you define bot behavior using registry-resolved script commands instead of writing a Python event handler for every single command. Commands are written as plain text script lines; each line is a function call, and functions are resolved from a shared FunctionRegistry at execution time.

Because FlowBot extends discord.ext.commands.Bot directly, nothing about normal discord.py development goes away — cogs, listeners, app commands, and regular @bot.command() functions all continue to work side by side with script commands. Tflows is meant to sit on top of discord.py for automation and rapid iteration, not to replace it.

🐢 Traditional discord.py

  • Per-command async function callbacks
  • Manual ctx.send() and Embed construction
  • Verbose context lookups for author/guild/channel
  • Restart usually required to change command text

⚡ Tflows Scripting

  • Commands registered via bot.command(name, code, ...)
  • Functions and variables resolved from a shared registry
  • $variable interpolation resolved by the Engine
  • Custom functions still get full access to discord.py via FlowContext

Key Features

📝

Script Commands

Register commands with bot.command(name, code, description="", aliases=()).

⚙️

Registry-Driven Engine

Every function and variable call is resolved from a FunctionRegistry at execution time.

🧩

Extensible

registry.register() and registry.register_var() let you add your own functions and variables.

🏷️

Aliasing

register_alias and register_var_alias give existing entries friendlier names.

🔒

Isolated Registries

Pass registry=FunctionRegistry() to keep a bot's function set separate from the defaults.

🤝

Fully Compatible

FlowBot is a commands.Bot subclass — cogs, listeners, and app commands all still work.

Who is it for?

Tflows is for developers who want to ship straightforward commands quickly without writing an async function for each one, while keeping full discord.py available for anything more involved. It's a good fit for bots with a lot of small, similar commands — greetings, status messages, moderation shortcuts — where a script line is faster to write and easier to review than a full command function.

Tflows wraps discord.py and requires Python 3.8+ along with a valid Discord bot token.

Quick Start #

Below is a minimal working bot. It registers a single !test command that replies with a message showing current latency.

python · main.py 
from tflows import FlowBot

bot = FlowBot(prefix="!")

bot.command(
  "test",
  """
send Hello World $ping
"""
)

bot.run("YOUR_BOT_TOKEN")

Trigger it in Discord with !test. The bot replies: Hello World 42 (latency will vary).

Never hard-code your bot token in source files. Use environment variables or a .env file with python-dotenv.

A richer example with an embed

tflows script 
embed
title Server Status
desc Latency: $pingms
desc Server: $server
desc Members: $membercount
desc Time: $time(24h)
endembed
Core

Architecture #

Tflows is organized around four pieces that work together on every command invocation: FlowBot, the Engine, FlowContext, and the FunctionRegistry. Understanding how they relate makes it much easier to reason about custom functions, isolated registries, and error handling.

Message
prefix + name
→
FlowBot
command lookup
→
FlowContext
built per call
→
Engine
line-by-line
→
FunctionRegistry
resolve calls
→
Discord
send / react / etc.

Components

class

FlowBot

The main bot class. Extends discord.ext.commands.Bot, adds .command(name, code, ...) for script registration, and owns the default FunctionRegistry.

class

Engine

The script interpreter. Executes a command's script text line by line against a FlowContext, resolving variables and dispatching function calls.

class

FlowContext

The execution context passed to every function and variable. Carries the real discord.py objects for this invocation — message, author, guild, channel, args.

class

FunctionRegistry

A lookup table of function and variable names to Python callables. Pre-loaded with built-ins by default, or supplied fresh for isolation.

module

tflows.builtins

Sets up the base registry with the standard library of functions and variables before any bot-specific code runs.

package

tflows.function

Additional function modules, discovered and loaded automatically, alphabetically by file name, at bot startup.

How a command flows through these pieces

1

Message received

A message arrives that matches the configured prefix and a registered command name.

2

Script lookup

FlowBot retrieves the stored script text for that command name (or alias).

3

Context built

A FlowContext is constructed for this invocation, wrapping the message, author, guild, channel, and parsed arguments.

4

Engine executes the script

The Engine walks the script line by line, resolving $variables and calling functions from the FunctionRegistry as it goes.

5

Output reaches Discord

Function calls like send, react, or an embed block use the real discord.py objects in the FlowContext to produce output.

Because FlowBot is a genuine commands.Bot subclass, none of this replaces discord.py's gateway handling — it only adds a script execution layer on top of a normal command invocation.

Core

FlowBot #

FlowBot is the main entry point. It subclasses discord.ext.commands.Bot, so every normal discord.py feature — commands, cogs, listeners, checks, app commands — keeps working exactly as it would in a plain discord.py bot. On top of that, it adds script command registration and manages the shared FunctionRegistry.

python 
from tflows import FlowBot

bot = FlowBot(prefix="!")

bot.command(
    "greet",
    """
send Hi $id(user)!
""",
    description="Greets the invoking user.",
    aliases=("hi",)
)

bot.run("TOKEN")

Constructor

ParameterTypeDescription
prefix str The command prefix, e.g. "!", "?", "..".
help_command HelpCommand | None Overrides or disables the built-in help command. See Help System.
log_errors bool Catch and log exceptions raised during script execution instead of letting them propagate.
log_unknown_functions bool Log calls to unregistered function names instead of silently skipping them.
case_insensitive bool Match command names case-insensitively, passed through to the underlying commands.Bot behavior.
members_intent bool Enables the guild members intent, required for accurate member-based variables like membercount breakdowns.
registry FunctionRegistry Optional. Supply a pre-built registry for isolated function sets. See Isolated Registries.

See FlowBot Options for a deeper look at how each of these affects runtime behavior.

Script Commands #

Script commands are registered with bot.command():

python 
bot.command(
    name,
    code,
    description="",
    aliases=()
)
ParameterTypeDescription
name str The command's trigger name, invoked as {prefix}{name}.
code str The script text — usually a triple-quoted multi-line string.
description str Optional. Shown in the help command output.
aliases tuple Optional. Alternate names that trigger the same script.
python 
bot.command(
    "greet",
    """
send Hello, $user!
""",
    description="Greets the user who ran the command.",
    aliases=("hi", "hello")
)

Because FlowBot extends commands.Bot, script commands live in the same namespace as regular discord.py commands — you can freely mix the two on the same bot. See Mixing with discord.py for patterns.

Core

Execution Model #

The Engine treats a script as a sequence of lines executed top to bottom. Each non-empty, non-comment line is a function call; the first token is the function name and the rest of the line is passed as arguments.

tflows script 
send Hello there!
react 👍
wait 2

Variable resolution

Variables are written as $name or $name(arg) and are resolved before the line's function is called. Built-in examples include $user, $server, $args, $ping, and $command.

tflows script
send Welcome to $server, $user!
send Your command arguments were: $args

If a variable name isn't recognized, it's left in the output unchanged rather than raising an error. This makes typos and unregistered variables obvious in testing without crashing the command.

Comments

Three comment styles are supported. Any of them can annotate a script without affecting execution:

tflows script
// this is a comment
# this is also a comment
-- this is also a comment

Unknown functions

If a line calls a function name that isn't in the registry, the Engine does not crash the whole bot. Depending on the log_unknown_functions option, the call is either silently skipped or logged, and execution of the rest of the script continues. A single typo in one command won't take down every other command running on the bot.

Errors during execution

Errors raised inside a function during execution can be caught and logged rather than propagated as an unhandled exception, depending on the log_errors option — useful in production, where you'd rather see an error in your logs than have the bot silently stop responding to that command.

Core

Embed Blocks #

A script can build a rich Discord embed using an embed / endembed block. Inside the block, recognized fields are set line by line and sent as a single discord.Embed when the block closes.

tflows script 
embed
title Server Stats
desc Here's what's happening in $server right now.
color #5865F2
thumbnail $avatar
footer Requested by $user
endembed

Supported fields

FieldDescription
titleEmbed title. Supports variable interpolation.
descEmbed description. Multiple desc lines append to the description.
footerFooter text, shown at the bottom of the embed.
colorAccent color, given as a hex value.
thumbnailSmall image shown in the top-right of the embed. Accepts an image URL or a variable like $avatar.
imageLarge image shown at the bottom of the embed body.
authorAuthor line shown above the title.

Variables are resolved inside embed fields the same way they are on any other line, so $user, $server, and custom variables all work inside title, desc, and the other fields.

An embed block must be closed with endembed. Without it, the Engine won't know where the embed's field lines end and the rest of the script begins.

Extending

Custom Functions #

Register a new function into the registry with registry.register():

python 
def say_loud(ctx, *args):
    return " ".join(args).upper() + "!!!"

registry.register("shout", say_loud)

Once registered, shout can be called from any script the same way a built-in function is called:

tflows script
shout this is important

Custom functions receive the current FlowContext as their first argument, giving them access to the real discord.py objects for the invocation — ctx.channel, ctx.author, ctx.guild, and so on — so a custom function can do anything a normal discord.py command could do.

python 
def timeout_user(ctx, member_id, minutes):
    member = ctx.guild.get_member(int(member_id))
    # perform a real discord.py action using ctx.guild, ctx.channel, etc.
    return f"Timed out {member.display_name} for {minutes} minutes."

registry.register("timeout", timeout_user)

This is the intended way to use Tflows for anything beyond simple text or embed output: write a script line as the trigger, and let a registered Python function do the real work using full discord.py access.

Extending

Custom Variables #

Register a new variable with registry.register_var():

python 
def nickname(ctx):
    return ctx.author.display_name

registry.register_var("nick", nickname)

This makes $nick available inside any script:

tflows script
send Welcome back, $nick!

Custom variables work exactly like built-in variables once registered — they can appear standalone, inside embed fields, or as arguments to other function calls.

Extending

Aliases #

Give an existing function or variable an additional name without duplicating its implementation, using register_alias and register_var_alias:

python 
registry.register_alias("yell", "shout")
registry.register_var_alias("name", "nick")

After this, yell behaves identically to shout, and $name resolves the same way as $nick. Aliases are useful when you want a friendlier or shorter name for users writing scripts, without maintaining two separate implementations.

Extending

Isolated Registries #

By default, FlowBot creates and owns a single shared FunctionRegistry that is pre-loaded with all the built-ins. If you're running multiple bots in the same codebase, or you want to strictly control what functions a particular bot can call, pass in your own registry instance:

python 
from tflows import FlowBot, FunctionRegistry

custom_registry = FunctionRegistry()
custom_registry.register("shout", say_loud)

bot = FlowBot(
    prefix="!",
    registry=custom_registry
)

Constructing a fresh FunctionRegistry() does not automatically include the standard built-ins unless your setup explicitly loads them onto it — this is what "isolated" means here.

Isolation is useful for testing a minimal function set, or for embedding Tflows scripting into a larger application where you want tight control over exactly what a script is allowed to do.

Built-in Modules #

FlowBot automatically loads a default set of functions and variables at startup from two places:

module

tflows.builtins

Sets up the base registry — this is where the standard library of functions and variables gets registered before any bot-specific code runs.

package

tflows.function

Additional function modules are discovered and loaded dynamically during startup, in alphabetical order by file name. If a module fails to import or initialize, the failure is logged and loading continues with the rest.

This means the built-in function set can grow over time without changing how FlowBot is constructed — new modules under tflows.function are picked up automatically.

Module summary

ModulePurpose
sendSend a plain text message to the current channel.
replyReply directly to the message that invoked the command.
logPrint debug output while developing a script.
waitPause script execution for a given duration before continuing.
reactAdd one or more reactions to the invoking message.
deleteDelete a specific message.
clearPurge a number of messages from the current channel.
pingReport the bot's current latency.
timeReturn the current time, with optional formatting.
uptimeReturn how long the bot process has been running.
userAccess information about the command's invoking author.
guildAccess information about the current server.
channelAccess information about the current channel.
membercountReturn member counts for the guild, optionally filtered.
image / avatarReturn a profile image or avatar URL.
idReturn a Discord snowflake ID for the author, a mentioned user, or another target.
randomGenerate random values for use in scripts.
botinfoReturn information about the bot itself.
embedThe embed / endembed block described in Embed Blocks.

Other modules may exist under tflows.function beyond this list — since modules are loaded automatically, check your installed package for the current full set if you need something not listed here.

Help System #

FlowBot's built-in help command lists registered script commands alongside any regular discord.py commands on the bot. For each script command, the help output can show:

  • The command name and any registered aliases
  • The description passed to bot.command()
  • Basic usage information
  • In some cases, the underlying script source, useful for debugging or for letting trusted users see exactly what a command does

If you want full control over how help is presented, or you're integrating Tflows into a bot that already has its own help system, pass help_command=None (or your own HelpCommand subclass) when constructing FlowBot.

python 
bot = FlowBot(
    prefix="!",
    help_command=None  # disable built-in help
)

Variables #

Variables are special tokens embedded in your scripts, prefixed with $. They are resolved at runtime against the live FlowContext and replaced with their current values before output is generated.

Variables come in three flavors: static (no arguments, always produce the same type of value), function (accept an optional mode flag in parentheses), and dynamic (multiple formatting modes, such as time-based output).

$ping

static

Returns the bot's current WebSocket latency in milliseconds as a rounded integer string.

UsageReturns
$pingLatency in ms, e.g. 42
tflows script
send Pong! $pingms

$user

function

Returns information about the command's invoking author. Defaults to the author's display name.

ModeDescription
$user defaultAuthor's display name
$user(name)Author's raw username
$user(mention)Author mention string
tflows script
send Welcome, $user!

$server

function

Returns information about the current Discord guild (server). Defaults to returning the server name.

ModeDescription
$server defaultGuild name
$server(name)Explicitly returns the guild name
$server(boost)Current number of Nitro boosts
$server(boostlvl)Current boost tier level (0, 1, 2, or 3)
tflows script
$server
$server(name)
$server(boost)
$server(boostlvl)

$args

static

Returns the raw text the user typed after the command name — everything following {prefix}{name}, unparsed.

UsageReturns
$argsRaw argument string, e.g. spam bot 15
tflows script
warn $args

$command

static

Returns the name of the command currently being executed — the registered name, not the alias the user typed, if any.

UsageReturns
$commandCommand name, e.g. greet

$uptime

dynamic

Returns how long the bot has been running since startup. Supports multiple formatting modes including full, short, clock, seconds, and custom token-based output.

Usage Returns
$uptime Default format, e.g. 1h 23m 10s
$uptime(full) Full format including days, e.g. 0d 1h 23m 10s
$uptime(short) Compact format, e.g. 1h 23m
$uptime(clock) Clock-style format, e.g. 01:23:10
$uptime(seconds) Raw uptime in seconds, e.g. 4990
$uptime(d, h, m, s) Custom formatted output using tokens
tflows script 
embed
title Uptime Variants
desc Default: $uptime
desc Full: $uptime(full)
desc Short: $uptime(short)
desc Clock: $uptime(clock)
desc Seconds: $uptime(seconds)
desc Custom: $uptime(d, h, m, s)
endembed

$log

function

Sends a message to a specific Discord channel for tracking command usage, user actions, and bot events. Unlike console logging, this outputs directly inside a server channel.

Parameter Description
CHANNEL_ID Target Discord channel ID where the log message will be sent
MESSAGE Content of the log message
tflows script 
$log(CHANNEL_ID){User executed a command}

Behavior

  • Sends a message directly to the specified Discord channel
  • Executes when the command runs successfully (unless wrapped in error handling logic)
  • Supports variables like $user, $time, and other engine variables
  • Does not print to console, only sends to Discord channels

Examples

tflows script 
$log(123456789012345678){User executed !ping command}
tflows script 
$log(123456789012345678){$user used a command at $time}
tflows script 
$log(987654321098765432){$user was warned by $id for spam}

Notes

  • Bot must have permission to send messages in the target channel
  • If the channel ID is invalid, logging may silently fail or throw an error depending on configuration
  • You can use <@$id> to mention the command user since $id returns a raw ID

$image

function

Returns a Discord CDN avatar image URL. Accepts an optional mode flag to control whose avatar is returned. $avatar is registered as an alias of this variable.

ModeDescription
$image defaultCommand author's avatar URL
$image(user)Same as default — author's avatar
$image(mention)First mentioned user's avatar. Falls back to author if no mention.
$image(act)Mentioned user's avatar if a mention is present, otherwise author's.
tflows script
$image
$image(user)
$image(mention)
$image(act)

$membercount

function

Returns the guild member count. Can be filtered to include all members, only humans, or only bots. Requires members_intent=True for accurate human/bot breakdowns.

ModeDescription
$membercount defaultTotal member count (humans + bots)
$membercount(all)Same as default
$membercount(user)Count of non-bot members only
$membercount(bots)Count of bot accounts only
tflows script
$membercount
$membercount(all)
$membercount(user)
$membercount(bots)

$time

function

Outputs the current date and/or time. Accepts flags to control format; multiple flags can be combined with a semicolon delimiter.

ModeDescription
$time() defaultFull date + time in the default format
$time(12h)12-hour clock format (AM/PM)
$time(24h)24-hour clock format
$time(nodate)Time only — date portion omitted
$time(notime)Date only — time portion omitted
$time(nodate;24h)Combine flags with ; for composed output
tflows script
$time()
$time(12h)
$time(24h)
$time(nodate)
$time(notime)
$time(nodate;24h)

$id

function

Returns a Discord user ID as a string. Accepts an optional mode to select which user's ID to return.

ModeDescription
$id defaultCommand author's Discord user ID
$id(user)Same as default
$id(mention)First mentioned user's ID. Falls back to author if no mention.

Mixing with discord.py #

Because FlowBot is a subclass of commands.Bot, script commands and regular discord.py commands, cogs, listeners, and app commands all coexist on the same bot without any special handling.

Normal command alongside a script command

python 
@bot.command()
async def python_ping(ctx):
    await ctx.send(f"Pong! {round(bot.latency * 1000)}ms")

bot.command(
    "ping",
    "send Pong! $ping ms"
)

Listeners

Listeners work exactly as in discord.py:

python 
@bot.event
async def on_member_join(member):
    channel = member.guild.system_channel
    if channel:
        await channel.send(f"Welcome, {member.mention}!")

Cogs

Cogs work exactly as in discord.py, and can even register script commands during setup by calling bot.command() from within the cog's __init__, since bot.command() is just a method on the FlowBot instance:

python 
class Moderation(commands.Cog):
    def __init__(self, bot):
        self.bot = bot
        bot.command(
            "rules",
            "send Please review the server rules in #rules."
        )

    @commands.command()
    async def warn(self, ctx, member: discord.Member, *, reason):
        await ctx.send(f"{member.mention} was warned: {reason}")

bot.add_cog(Moderation(bot))

Custom functions calling into discord.py

Custom functions registered into the registry can call straight into discord.py from inside the FlowContext, so a script command can trigger arbitrarily complex Python logic while still being invoked as a simple script line — see Custom Functions for the full pattern.

Best Practices #

Following these patterns will make your Tflows scripts more readable, maintainable, and robust.

🎯

Keep scripts short and single-purpose

If a script is doing several unrelated things, it's often a sign that logic should move into a custom function instead.

🧩

Prefer reusable custom functions over duplication

If two commands both need the same lookup or action, register it once as a custom function rather than copy-pasting script lines.

🏷️

Use aliases for friendlier command and variable names

register_alias and register_var_alias let you expose short, user-friendly names without renaming the underlying implementation.

🔐

Validate arguments before acting

Especially for destructive functions like delete or clear — validate inside the custom function before performing the action.

📦

Store larger scripts in separate files

For bots with many commands, keep script text in .txt or .flow files and load them with open().read() to keep your main Python file clean.

🧪

Separate reusable logic from one-off scripts

Reusable custom functions belong in their own module that can be imported and registered into multiple bots' registries — don't bury them inside a single bot's setup file.

Guide

Debugging & Errors #

A few habits make debugging scripts and handling errors much less painful:

🪵

Enable log_errors and log_unknown_functions in development

They turn silent failures into visible ones, which is almost always what you want while writing new scripts.

🖨️

Use the log function to print intermediate values

Print values from inside a script while you're figuring out why a command isn't behaving as expected.

🛑

Catch expected failures inside custom functions

A bad ID, a missing permission, a network hiccup — catch the specific exception and return a clear, user-facing message rather than letting a raw traceback leak into script output.

🧫

Test new variables in isolation

Try a throwaway command like send Value: $newvar before wiring a new variable into a more complex embed or multi-line script.

🔇

Tune logging for production

Once a bot is live, consider routing log_unknown_functions output to a private log channel instead of the console, so a stream of user typos doesn't drown out real errors.

Common Mistakes #

These are the most frequent errors new Tflows users encounter, and how to fix them.

Forgetting to close an embed block

An embed block that is never closed with endembed leaves the Engine unable to tell where the embed's fields end and the rest of the script begins.

incorrect
# ❌ missing endembed
embed
title My Title
desc My description
correct
# ✅ block properly closed
embed
title My Title
desc My description
endembed

Registering a variable through registry.register() instead of register_var()

Functions and variables are tracked separately in the FunctionRegistry. A callable registered with register() is only reachable as a function call, not as a $variable.

incorrect
# ❌ won't be usable as $nick
registry.register("nick", nickname)
correct
# ✅ usable as $nick
registry.register_var("nick", nickname)

Assuming an isolated registry includes the built-ins

A freshly constructed FunctionRegistry() is empty — passing it to FlowBot does not implicitly load send, embed, or any other built-in unless your setup explicitly registers them onto it.

If scripts on an isolated-registry bot report every function as unknown, check whether the built-ins were actually loaded onto that registry.

Incorrect mode flag names

Mode flags are case-sensitive and must match the documented identifiers exactly. Check the Variables reference for the exact spelling.

incorrect
$membercount(users)   # ❌ should be "user"
$image(Mention)       # ❌ should be lowercase "mention"

Using mention without an actual mention

$id(mention) and $image(mention) fall back to the author if no mention is present — but the fallback exists to prevent crashes, not to produce the expected output. If you need flexible mention handling, use act mode instead and document the expected usage.

Combining a script command with a discord.py cog

python · main.py
import discord
from discord.ext import commands
from tflows import FlowBot, FunctionRegistry

registry = FunctionRegistry()

def nickname(ctx):
    return ctx.author.display_name

registry.register_var("nick", nickname)
registry.register_var_alias("name", "nick")

def warn_user(ctx, member_id, *reason_words):
    reason = " ".join(reason_words) or "No reason given."
    return f"<@{member_id}> has been warned: {reason}"

registry.register("warn", warn_user)

bot = FlowBot(
    prefix="!",
    log_errors=True,
    log_unknown_functions=True,
    case_insensitive=True,
    members_intent=True,
    registry=registry
)

bot.command(
    "welcome",
    """
// greets the user with their display name
embed
title Welcome!
desc Hey $nick, glad you're here in $server.
footer Member #$membercount(all)
endembed
""",
    description="Greets the invoking user."
)

bot.command(
    "warn",
    "warn $args",
    description="Warn a user by ID with a reason.",
    aliases=("w",)
)

class Moderation(commands.Cog):
    def __init__(self, bot):
        self.bot = bot

    @commands.command()
    async def kick(self, ctx, member: discord.Member, *, reason=None):
        await member.kick(reason=reason)
        await ctx.send(f"Kicked {member.display_name}.")

bot.add_cog(Moderation(bot))

@bot.event
async def on_member_join(member):
    channel = member.guild.system_channel
    if channel:
        await channel.send(f"Welcome to the server, {member.mention}!")

bot.run("YOUR_BOT_TOKEN")

This bot uses an isolated registry with a custom variable ($nick / $name) and a custom moderation function (warn), registers two script commands, and still has a fully normal discord.py cog and event listener running alongside them — demonstrating how Tflows scripting and standard discord.py code are meant to be used together rather than as alternatives to each other.
